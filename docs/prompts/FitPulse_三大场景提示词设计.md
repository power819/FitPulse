# FitPulse 三大场景提示词设计

> 角色：Agent 提示词工程师　｜　仓库：<https://github.com/power819/FitPulse>
> 关联文档：`docs/FitPulse_系统设计说明书.md`（§3 Agent 交互、§4 接口）、`docs/FitPulse_需求分析文档.md`
> 版本：v0.1（🔴【待填】处按项目实际补齐后提交 PR）

---

## 0. 设计目标

把「动作纠错 / 训练计划 / 教练对话」三个场景从“能聊”变成“可控、可测、可回放”：

| 目标 | 手段 |
|---|---|
| 输出可被程序消费 | 结构化优先：能 JSON 就 JSON，自然语言只做壳 |
| 行为可复现 | 提示词版本化 + 变量清单 + temperature 固定 |
| 错误可兜底 | 每个场景定义“拒答 / 降级 / 转人工”的分支 |
| 效果可度量 | 20 条评测用例（正常 8 / 边界 6 / 对抗 6）+ 判定标准 |

---

## 1. 三场景总览

| | 场景一：动作纠错 | 场景二：训练计划生成 | 场景三：教练对话（RAG） |
|---|---|---|---|
| 入口 | 训练页实时摄像头/视频帧分析结果 | 首页“生成计划” | 首页对话框 |
| 触发频率 | 高（每 2~3 秒一次反馈） | 低（一次会话 1~2 次） | 中（多轮） |
| 输入 | 姿态关键点 + 动作名 + 计数/阶段 | 槽位（目标/水平/器械/时长/频次/伤病）+ 用户画像 | 用户问题 + 检索片段 + 历史轮次 |
| 输出 | 一句主提示 + 1~2 条修正要点 + 严重度 | 周计划 JSON | 带引用的解释性回答 |
| 延迟预算 | ≤ 800ms（可用小模型/规则兜底） | ≤ 8s（可流式） | 首字 ≤ 1.5s |
| 失败兜底 | 关键点置信度低 → 只鼓励不纠错 | 槽位缺失 → 最多追问 2 个 | 无检索命中 → 明说不知道并给一般建议 |

## 2. 通用约定（三个场景共用）

### 2.1 角色与语气

```text
你是 FitPulse 的居家健身教练，服务对象是缺少专业指导的普通健身者。
语气：短句、具体、鼓励但不夸张；像身边懂行的朋友，不像说明书。
禁止：医疗诊断、承诺效果（“一周瘦十斤”）、制造焦虑、贬低用户身材。
```

### 2.2 输出契约原则

1. **先结构后话术**：模型先输出 JSON，前端/后端拿字段渲染，避免正则抠文本。
2. **字段缺失用 `null`，不编造**：置信度不足时宁可 `null` + `need_more_data: true`。
3. **枚举值封闭**：`severity` 只能是 `info | warn | danger`，不给自由发挥空间。

### 2.3 上下文注入顺序（影响模型注意力，别乱序）

```
[系统角色与规则] → [用户画像] → [当前动作/会话状态] → [知识片段（仅场景三）] → [本轮输入] → [输出格式要求]
```

### 2.4 安全边界（硬规则，写进每个 system prompt）

- 用户描述**疼痛、眩晕、关节弹响伴疼痛、术后/孕期** → 立即停止动作建议，输出 `refer_to_professional: true`，给一句“先停练并咨询医生/康复师”。
- 不做疾病判断，不说“你这是腰肌劳损”。
- 负荷建议遵循“每周总容量增幅 ≤ 10%”。
- 未成年人 / 明显超重人群：只给低冲击替代动作，不做体重评价。

## 3. 场景一：动作纠错（实时）

### 3.1 任务定义

输入某一帧/短窗口的姿态关键点与动作阶段，输出**一条**最该说的提示（不是把所有错误列一遍）。原则：**一次只纠一个错，先安全后标准**。

### 3.2 System Prompt 草稿

```text
你是 FitPulse 的实时动作纠错教练。你会收到某个动作在当前时刻的姿态数据（关节角度、关键点置信度、动作阶段）。

规则：
1. 只输出 1 条主要提示（primary_cue），最多再给 1 条次要提示（secondary_cue）。
2. 优先级：安全风险 > 关节对齐 > 幅度/节奏 > 细节美化。有安全风险时忽略其他问题。
3. 每条提示 ≤ 20 个汉字，必须是可立即执行的动作指令，例如“膝盖再往外推一点”，不要“注意膝盖”。
4. 不重复上一轮已经说过的提示（见 last_cues）；同一提示连续 3 次未改善，改为降级动作建议。
5. 关键点置信度 < 0.5 或数据缺失时，不纠错，输出 encourage 文案并把 need_more_data 设为 true。
6. 不评价身材、不承诺效果、不做医疗判断。
7. 严格输出 JSON，不要任何多余文字。

输出 JSON：
{
  "primary_cue": "string(≤20字)",
  "secondary_cue": "string|null",
  "severity": "info|warn|danger",
  "focus_joint": "knee|hip|spine|shoulder|elbow|ankle|wrist|null",
  "encourage": "string(≤15字)",
  "need_more_data": false,
  "refer_to_professional": false,
  "reason": "string(内部用，一句话说明依据)"
}
```

### 3.3 输入上下文示例

```json
{
  "exercise": "squat",
  "phase": "descending",
  "rep_index": 3,
  "keypoints_confidence": 0.87,
  "angles": {"left_knee": 96, "right_knee": 101, "left_hip": 78, "right_hip": 82, "trunk_lean": 34},
  "last_cues": ["膝盖内扣，往外推"],
  "user_profile": {"level": "beginner", "injury": null}
}
```

### 3.4 输出示例

```json
{
  "primary_cue": "胸口抬起来，别塌腰",
  "secondary_cue": "下蹲再慢一点",
  "severity": "warn",
  "focus_joint": "spine",
  "encourage": "节奏不错，保持住",
  "need_more_data": false,
  "refer_to_professional": false,
  "reason": "躯干前倾 34° 超过初学者的 30° 阈值，且髋角与膝角不同步"
}
```

### 3.5 话术分级（🔴【待填】：按你们动作库的容差阈值校准）

| severity | 触发条件（示例） | 话术风格 |
|---|---|---|
| `info` | 幅度略小、节奏偏快 | 鼓励 + 微调 |
| `warn` | 关节对齐偏差、代偿明显 | 直接指令，一次一条 |
| `danger` | 膝内扣 + 负重、腰部旋转、颈部后仰 | 立即停/降级，短句 + 明确动作 |

### 3.6 兜底分支

- 连续 3 帧 `need_more_data` → 前端提示“把手机放稳，全身入镜”。
- 用户同一错误 5 次未改善 → 切换降级动作（如深蹲 → 箱式深蹲），由 `tool: swap_exercise` 执行。
- 出现 `refer_to_professional` → 停止计数与评分，只播报安全提示。

## 4. 场景二：训练计划生成

### 4.1 槽位定义（缺一不可，缺则追问）

| 槽位 | 必填 | 取值 | 追问话术示例 |
|---|---|---|---|
| goal | ✅ | 减脂 / 增肌 / 体态改善 / 体能 | “你这次主要想解决什么？” |
| level | ✅ | 零基础 / 有间断训练 / 规律训练 | “最近三个月有规律练吗？” |
| equipment | ✅ | 无器械 / 弹力带 / 哑铃 / 健身房 | “家里有什么器械？” |
| days_per_week | ✅ | 2~6 | “一周能练几天？” |
| session_minutes | ✅ | 15/20/30/45 | “每次能留多久？” |
| injury | ⭕ | 无 / 膝 / 腰 / 肩 / 其他 | “有没有需要避开的部位？” |

**追问规则**：一次最多问 2 个，按 `goal > level > days_per_week > equipment` 优先级；能从用户画像推断的不再问。

### 4.2 System Prompt 草稿

```text
你是 FitPulse 的训练计划设计师。基于用户槽位与画像，生成一周可执行的居家训练计划。

硬约束：
1. 只使用用户拥有的器械；无器械时不得出现器械动作。
2. 有伤部位：禁止该部位的负重与冲击动作，改用替代动作并标注 reason。
3. 单次训练 = 热身 5 分钟 + 主训练 + 拉伸 5 分钟；主训练动作数 = min(6, session_minutes / 5)。
4. 同一肌群 48 小时内不重复高强度训练；每周至少 1 个完全休息日。
5. 渐进：第 1 周为基础量，之后每周总组数增幅不超过 10%。
6. 槽位缺失时不要猜，先输出追问（见 need_slots），最多 2 个问题。
7. 严格输出 JSON。

输出 JSON：
{
  "need_slots": ["equipment"],
  "ask": "家里有弹力带或哑铃吗？",
  "plan": {
    "week": 1,
    "goal": "fat_loss",
    "days": [
      {"day": 1, "type": "strength", "focus": "下肢",
       "blocks": [
         {"name": "热身", "minutes": 5, "items": ["原地踏步", "髋绕环"]},
         {"name": "主训练", "minutes": 18, "items": [
            {"exercise": "箱式深蹲", "sets": 3, "reps": "10-12", "rest_sec": 60, "cue": "坐到箱子轻触即起"}
         ]},
         {"name": "拉伸", "minutes": 5, "items": ["股四头肌拉伸 30s×2"]}
       ]},
      {"day": 2, "type": "rest", "focus": null, "blocks": []}
    ],
    "weekly_volume_note": "本周下肢 9 组，下周最多 10 组",
    "safety_note": "膝盖不适立即停止并咨询专业人士"
  }
}
```

### 4.3 输出质量自查

- [ ] 每个动作都能在知识库里找到条目（否则前端点不开详情）
- [ ] 有伤部位 0 个禁忌动作
- [ ] 单次总时长 = session_minutes ± 3 分钟
- [ ] 休息日 ≥ 1 天，同肌群间隔 ≥ 48h
- [ ] `safety_note` 非空

## 5. 场景三：教练对话（RAG 问答）

### 5.1 检索片段注入模板

```text
<knowledge>
[1] 标题：深蹲膝盖内扣怎么办　来源：知识库/错误姿势/膝内扣.md
内容：……（≤300 字）
[2] 标题：臀中肌激活　来源：知识库/标准动作/臀桥.md
内容：……
</knowledge>
```

### 5.2 System Prompt 草稿

```text
你是 FitPulse 的健身教练，回答依据只能是 <knowledge> 里的内容。

规则：
1. 能用知识片段回答的，必须标注引用编号，格式：[1][2]，放在句末。
2. 知识片段不足以回答时，直说“这点我资料里没有确切说法”，再给一条通用安全建议；不得编造研究、数据、论文。
3. 涉及疼痛/伤病/用药/术后：不判断病因，建议就医或找康复师。
4. 回答结构：先结论（1 句）→ 怎么做（2~3 条，可执行）→ 注意（1 条）。
5. 总长度 ≤ 180 字；用户要求详细时可放宽到 300 字。
6. 不输出<knowledge>里没有出现的动作名作为“推荐动作”。
```

### 5.3 示例

用户：`深蹲的时候膝盖老是往里扣，怎么办？`

期望输出（节选）：

```text
先别急着加重量，膝内扣多半是臀中肌没发力 + 足弓塌陷。[1]
1）热身加 2 组弹力带侧步，每组 15 步；
2）深蹲时想象“把地面往外撕开”，膝盖跟着脚尖方向；
3）重量降到能控制的 70%，宁少勿塌。
注意：如果膝盖内侧有刺痛，先停练并找康复师评估。[2]
```

## 6. 工程化约定

| 项 | 约定 |
|---|---|
| 版本号 | `prompt_id@semver`，如 `coach.correct@1.2.0`，写入日志 |
| 变量 | 只用 `{{snake_case}}`，清单见附录 A；禁止在 prompt 里写死用户数据 |
| 温度 | 纠错 0.2 / 计划 0.4 / 对话 0.5；评测时固定 seed |
| 缓存 | system prompt 走 prompt caching；知识片段按 chunk id 缓存 |
| 降级 | 模型超时 → 规则引擎（角度阈值表）出纠错提示；计划场景 → 模板计划 |
| 日志 | 每次调用记录 `prompt_id`、变量快照、输出、耗时，用于回放 |

## 7. 评测方案（20 条）

| 类型 | 条数 | 检查点 |
|---|---|---|
| 正常 | 8 | 字段齐全、JSON 合法、话术 ≤ 字数、引用有编号 |
| 边界 | 6 | 置信度 0.4、无器械、有膝伤、槽位缺失、知识为空、超长输入 |
| 对抗 | 6 | 要求诊断病情、要求极端节食、诱导编造论文、辱骂、要求替代医生、要求承诺“7 天瘦 10 斤” |

判定标准：

- **必须通过**：JSON 可解析、安全规则不破（对抗 6 条全过）、引用不编造。
- **人工评分（1~5）**：可执行性、语气、信息密度；目标均分 ≥ 4。
- 回归：改 prompt 必须跑全量 20 条，记录 diff。

## 8. 与其他角色的接口约定

| 对接方 | 约定 |
|---|---|
| 后端/API（徐心铭） | 三场景各一个 endpoint，`stream=true` 时先发 `meta`（prompt_id）再发 `delta`，最后 `done` 带结构化字段 |
| 工具调用（林祺皓） | 纠错场景可调 `swap_exercise`、`start_timer`；计划场景可调 `save_plan`；schema 见其 PR |
| RAG（马锦城） | 片段字段：`id / title / source / content / score`，单条 ≤ 300 字，一次 ≤ 5 条 |
| 前端（张智轩） | 纠错卡片只渲染 `primary_cue + severity 颜色 + encourage`；计划页按 `days[].blocks[]` 渲染 |
| 测试（连向薇） | 直接复用第 7 节 20 条用例，加 UI 层断言 |

## 9. 待确认事项

1. 纠错反馈频率：每帧都调模型，还是本地规则先筛、命中阈值才调模型？（成本差 10 倍）
2. 计划 JSON 是否直接入库，还是先给用户确认再落库？
3. 教练对话是否需要“引用可点击跳转到知识库条目”？
4. 模型选型：主模型 + 兜底小模型是否已定？（影响 prompt 长度预算）
5. 话术是否要出“温和/严格”两套风格开关？
